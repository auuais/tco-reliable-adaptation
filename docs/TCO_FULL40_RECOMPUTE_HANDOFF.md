## 1. The claim to test

Can we process ten 392 × 518 images jointly, adapt LoRA throughout all 24 paired VGGT stages for 40 real TCO updates, and finish reconstruction on this card? Does the **same execution policy** preserve five-view quality relative to the optimized local full-40 reference? Treat “within 1%” as a **noninferiority margin**. Each mean surface distance may rise by at most 1% relative to its own reference. A larger improvement is welcome. Measure any slowdown. The primary goal has no speedup threshold.

Give separate verdicts for ten-view fit, five-view accuracy, five-view completeness, and what recomputation adds over ordinary head chunking. A useful engineering result could be that changing the depth head's chunk size suffices. A strong joint claim needs repeatable ten-view fit and evidence for both five-view endpoints. Five-view parity establishes quality at five views only. If the ten-view control fits, measure its quality directly as well.

[Upstream TCO at the pinned revision](https://github.com/cvlab-stonybrook/TCO/blob/65387333877723cf99086f7f29089379dd50c59a/tco_vggt_lora.py) |

The native maximum is eight frames per depth-head call, so ten views use 8+2 and five use 5. After joint attention, the depth head decodes each view spatially. Smaller chunks change the size of temporary convolution tensors. Recomputing a chunk during backward can also release activations saved by autograd. |
| Invariants | Head parameters stay frozen while gradients pass **through** the head to the four taps and all LoRA factors. Reassemble all depth and confidence outputs in original view order before the single joint TCO loss. Keep every pixel, view and update, native model precision, renderer group count and optimizer step. The existing patch-embed CPU placement is part of the matched baseline. Additional CPU offload, split global attention, reduced resolution or detached taps would answer a different question. |

For a frozen depth head with predictions `d = h(z)` and upstream loss derivative `g`, the gradient required by the backbone is `J_h(z)^T g`. Recomputing the same head operations during backward should recover that product with less saved storage. Smaller frame batches can change convolution kernels and floating-point accumulation. Verify same-chunk recomputation fidelity first, then measure end-to-end quality against the native reference. [Pinned PyTorch checkpoint implementation](https://github.com/pytorch/pytorch/blob/v2.7.1/torch/utils/checkpoint.py)

## 4. Profile the full run and separate the two interventions

1. **Reproduce the reference.** On Heads/seq-01, seed 42, run a clean, uninstrumented five-view full 40 and attempt the original ten-view full 40. 2. **Build a memory timeline.** Mark placement and patch extraction, initial no-grad prediction, joint transformer, camera head, each DPT chunk and the high-resolution fusion, loss/gsplat rendering, backward, clipping/Adam, final readout and unprojection. Capture the first two steps, a middle step and step 40 in a complete five-view profile. Adam state appears after the first update. At ten views preserve the last completed phase, iteration, chunk index, request size and allocator state on OOM. Use diagnostic-only synchronized phase boundaries, allocated/reserved/current/peak bytes, device free memory and host RSS. Use a bounded allocator snapshot or saved-tensor inventory on a separate probe if necessary. Deduplicate shared storages and avoid retaining tensor references in logging hooks. An allocator snapshot can miss external CUDA allocations. Compare instrumented and clean outcomes if instrumentation shifts the peak. [PyTorch memory snapshot guidance](https://docs.pytorch.org/docs/stable/torch_cuda_memory.html)
3. **Screen the factorial below.** On the development Heads window, compare native DPT chunk size 8 and smaller maxima 4, 2, 1, each with DPT recomputation **off and on**. The native/off cell is the reference. This is an eight-cell screen, including chunk-only and recompute-only controls. Use at most two real updates per initial timing/memory probe, including a backward and optimizer step whenever feasible. These probes collect no scientific surface scores. Preserve failure receipts. The chosen maximum applies to both five and ten views, with a smaller final chunk when needed.
4. **Implement recomputation around one DPT chunk.** Use explicit four-tap tensor arguments, image slice and fixed bounds, with `torch.utils.checkpoint.checkpoint(..., use_reentrant=False, preserve_rng_state=True)`. Keep the graph connected and retain native autocast settings. A safe implementation slices each tap and the images **once**, rebuilds the sparse tap list and calls the native head kernel with local bounds. Binding each chunk's indices at construction avoids replaying the last chunk for every backward call. Return depth and confidence, concatenate each once along the view dimension, and leave RNG-consuming rendering outside this closure. Apply the selected chunk maximum during initial, update and final head passes. Enable recomputation only for the gradient-bearing update head. Count closure entries in a qualification run to verify actual backward replay. PyTorch can stop replay after it has regenerated the needed tensors.
5. **Promote using resources only.** Within the recomputation-on and off families, order successful ten-view probes by synchronized step time, then lower peak allocated memory, then larger chunk. Run each provisional winner for a clean 40 updates on Heads. If it fails at a later phase, advance to the next eligible cell in that family. Run the same-chunk off comparator for the winning on policy and preserve its failure if it cannot finish. Repeat the clean full-length resource readings for the leading feasible on/off policies in three fresh processes at seed 42 and report medians and spread. Freeze the first qualified policy in each family according to the registered ordering. Keep chunk-only results visible even if they win. Do not read surface scores to choose policies.
6. **One bounded fallback.** If all depth-head recomputation policies fail to finish ten views, use the profiles to decide whether transformer checkpoint boundaries still live at the limiting phase account for enough bytes to justify one additional design. If so, register a policy with four non-overlapping joint-stage segments ending at taps 4, 11, 17 and 23, plus the lowest-peak qualified DPT setting from the five-view probe. Return segment tokens and taps as explicit outputs. Replace inner block checkpoints within these segments to avoid redundant nested replay. Preserve frame/global attention shapes and order. Compare against the identical DPT policy without grouped stages. If a no-grad final readout or an irreducible operator workspace dominates, document that peak and the remaining headroom. The study can conclude with a measured limit. For ranking failed ten-view policies, run matched five-view probes so the peak and timing comparisons come from complete runs.
