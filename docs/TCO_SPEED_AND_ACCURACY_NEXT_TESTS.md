# Two experiments for faster and more accurate five-view TCO

Research proposal, 28 November 2026. Start on the local 10 GiB RTX 3080 with public scenes. The first experiment measures geometry at a speed and memory budget. The second asks whether we can surpass the geometry of full TCO when computation is available. Each has its own success criterion.

## What the fast result establishes

The fast model performs ten real Adam updates on LoRA in the final 12 VGGT stages and reuses features from the frozen early stages. The full TCO reference adapts LoRA across all 24 stages. All adapted runs in this comparison receive five RGB frames and camera pose and intrinsics priors. Zero-step VGGT predicts from the images. Reference depth and surfaces enter the evaluator only. The original TCO paper also gives a baseline which backprojects frozen VGGT depth using supplied cameras. Include that inexpensive prior-aware baseline in the next comparison. [TCO paper](https://openaccess.thecvf.com/content/CVPR2026/papers/Zhou_Learning_3D_Reconstruction_with_Priors_in_Test_Time_CVPR_2026_paper.pdf)

Three baselines matter. At equal ten updates, caching saved 29.0% of scene time on 7-Scenes and 31.8% on ETH3D, while accuracy/completeness errors increased 11.18%/6.90% and 54.93%/88.35%, respectively. At approximately equal elapsed time, ordinary TCO at five updates on 7-Scenes or four on ETH3D also had better average geometry, while using more memory. ## Experiment A — recover geometry at the cached runtime

**Hypothesis.** The cached model saves time by reusing early features. Restricting those features to their pretrained values for an entire scene may explain part of the geometry loss. Test whether one opportunity for early correction is enough, and separately whether the stronger model can teach a better starting point for the same cheap inference graph.

1. **First screen.** On an existing development room, compare ordinary 10, cached 10, and a hybrid with an all-stage LoRA update on step 1 followed by nine cheap suffix updates. Also test the hybrid with caching disabled and the same weight-update schedule. Freeze the early adapters and their Adam state during cheap updates. Build the cache after the early update. Invalidate it when upstream weights or the applicable view configuration change. Confirm ten optimizer updates, identical sampling and final FP32 readout. Time the whole scene, including the refresh and reconstruction. Measure peak live and reserved memory. One full backward can set the entire scene's memory peak.
2. **Choose the follow-up by observation.** If the one-refresh run fits but buys little geometry, compare one further refresh at step 6 on development. If a full refresh sacrifices the resource advantage, test updating a small group of middle stages or a checkpointed refresh. Treat each as a distinct method and record the new time and peak. Keep the existing cached implementation as the reference.
3. **If the exact inference budget is decisive, test offline distillation.** Generate full-40 reconstructions on separate public training scenes. Learn only an initialization for the existing suffix adapters from the teacher's gauge-aligned depth and relative camera predictions. At deployment perform the same ten cached updates with the same graph. Compare standard initialization, initialization trained for the same offline compute using the original TCO objective, and teacher-trained initialization. Keep all windows of a physical scene within one split. Account separately for offline data and teacher cost. This is a route to preserving inference resources even if a refresh proves too expensive.
4. **Decision.** First report measured speed and memory against full 40, using about 4× and 23.6% as the historical targets. Use full 10 for the equal-update geometry test, with a one-sided 95% upper bound at or below +1% accuracy and +3% completeness. Separately apply those margins against full 40 to assess whether full-length reconstruction quality has been recovered. Include the best ordinary TCO setting affordable at the candidate's measured time and a measured common memory cap. At a fixed cap, report completion fractions for every arm. Report a speed/quality/memory trade-off wherever a target is missed.

## Experiment B — beat full TCO on surface accuracy

**Hypothesis.** Different ordinary TCO runs sometimes make different local depth errors. A robust combination in a common camera frame may reduce error, even if a single run's loss cannot tell which prediction to trust. This is a hypothesis about adapted TCO outputs. The project already tested anchor-order ensembles of frozen VGGT. [Earlier anchor-order protocol](ANCHOR_ORDER_DEPTH.md)

1. **Start with saved outputs.** On the three development rooms in the caching study, retrospectively picking the most accurate full-40 seed in each room with ground truth gives a 7.70% accuracy improvement relative to the mean individual seed error. The change varies from 2.25% to 16.62% across rooms. This diagnostic uses the answer key. It estimates the opportunity for choosing among existing runs and says nothing by itself about what an inference algorithm can recover. [Development rows](../results/tco_one_percent_v1/evidence.json)
2. **First real test costs no new GPU inference.** Use three independently adapted full-40 predictions per room. Bring clouds into a common gauge using the supplied camera rig, reproject to fixed target cameras using visibility checks, and take a per-pixel median of valid positive log depths. Choose the anchor and fallback rule before scoring. Use the anchor where fewer than two runs support a pixel. Use the same emitted pixels and count in every comparison. Evaluate standard TCO, each individual input run after the same reprojection, and three copies of one run through the same fusion code. Apply the same final evaluator to every arm. This separates gains due to the supplied cameras, a change in point density, or reprojection from gains due to combining independent predictions. Check well-supported and occluded surfaces separately on development.
3. **Test a single-trajectory mechanism if fusion helps.** Keep ordinary all-stage LoRA and save updates 24, 32 and 40 of one forty-update trajectory. Compare the final iterate, output fusion of these three checkpoints, and averaging the effective LoRA weight changes at those checkpoints. For a LoRA change proportional to BA, average the products BA. The product of the separately averaged B and A need not equal the average effective change. Hold camera alignment, output pixels and readout fixed. Charge all readouts to the measured runtime. Averaging is an established idea; the scientific question is whether it corrects the geometry of scene-specific TCO updates. [Weight averaging](https://proceedings.mlr.press/r16/izmailov18a.html)
4. **Decision.** Primary comparator is standard full TCO at 40. If the candidate uses three full trajectories, also run ordinary TCO at a comparable total compute budget and report elapsed time. Declare improved accuracy only when the one-sided 95% upper bound for the paired candidate-to-TCO mean accuracy error ratio is below 1.00 on fresh rooms. Guard completeness at +3% and report its actual effect. For a claim of better geometry in both directions, require both upper bounds below 1.00. Fix point support and report valid-point counts so deleting difficult geometry cannot manufacture an accuracy gain.

## Order, evaluation and publication

Run the archived CPU fusion check and the one-refresh RTX 3080 development screen first. Retain the full list of attempted settings and failures. Use previously examined rooms for diagnosis only. Before scoring new scenes, freeze one candidate per direction, the input/prior policy, score, seeds, timing boundaries, promotion criteria and new scene lists. Use the same five inputs, camera priors, hardware, precision and scorer across matched methods. Start with three paired seeds and at least six fresh public physical scenes per confirmation dataset where available. Estimate uncertainty from paired scenes and seeds, separately by dataset; add more independent scenes if bounds remain wide. Report millimetres, per-scene relative changes, tail failures, time per scene and peak live GPU memory. Use public calibrated inputs for the main claim and add a pose/intrinsics perturbation sensitivity if claiming robustness to imperfect calibration.

For the efficiency paper, show absolute axes for latency, surface accuracy, completeness and peak memory, including both VGGT references, full TCO at 4/5, 10 and 40 updates, and candidate settings. For the accuracy paper, report a head-to-head with independently repeated full TCO and a comparable-compute control. A quality improvement that costs additional time can succeed in Experiment B. An improvement over VGGT that also loses to ordinary short TCO at the same time supports a narrower memory-constrained claim in Experiment A. All proposed screens use local resources; rental spend for this proposal is USD 0.
