# Can cached TCO recover full-decoder reconstruction quality?

**Experiment handoff for SOL · 23 November 2026 · Planning only**

Run this study after the user resumes the goal. Use one local RTX 3080 (10 GiB), public data, and **USD 0 RunPod spend**. A reproducible negative or inconclusive result completes the study. The first milestone is a committed development registration and passing engineering checks. The last is a public CPU-replayable verdict. The study ID is `tco_one_percent_v1`.

## The question and what would count as a result

Can five-view VGGT/TCO with clean camera poses and intrinsics produce a usable point cloud in **at most half the scene time**, with **at most 80% of the peak allocated GPU memory**, while keeping **both mean surface distance errors within 1% relative of optimized full 40-step TCO**? Lower is better on all four measurements. Compare with a shorter full-decoder run that also fits the candidate's time budget. Separately test whether using true cross-view correspondences explains any benefit from a new adapter.

The previous study is the starting evidence. Cached last-12 at ten updates was 4.79–5.21× faster and used 5.98 GiB against 7.83 GiB for full 40. Accuracy error rose 1.96–2.26%, while completeness rose 0.27–0.99%. Chess lost 4.46% in accuracy and 11.83% in completeness. Heads improved on both. Using 40 cached updates increased the aggregate accuracy error further. With the same trainable suffix, caching alone saved 30.4% of ten-step latency and changed peak allocation by less than 0.01%. The memory target leaves roughly **0.28 GiB** above the existing cached path. The ranges bound a missing baseline repeat. Use fresh matched controls for this study. [Benchmark](../results/tco_frozen_prefix_v1/README.md) · [Per-room evidence](../results/tco_frozen_prefix_v1/allocator_sensitivity_decision.json)

Three explanations are worth distinguishing. A slightly different cutoff or step count may already suffice. An ordinary extra low-rank adapter may restore useful capacity. Features from corresponding patches across views may supply additional geometric information. Test them in that order. Prior work already covers caching or low-rank visual adaptation. A contribution here would be a measured quality guarantee on a stated population or evidence for a specific multiview correction under the same cost. [TCO](https://arxiv.org/abs/2604.03878) · [LoSA](https://arxiv.org/abs/2402.02887) · [StreamTTO](https://arxiv.org/abs/2603.01765)

## 4. Implement the correction

The last-12 model freezes paired stages 0–11. Correct only the patch tokens of the **raw post-global output of stage 11** entering stage 12. Keep camera/register tokens, position indices, and frozen depth-head taps 4 and 11 unchanged. Live taps 17 and 23 and the camera head see the corrected suffix. For last-14 the start index is 10, so frozen stages are 0–9, only tap 4 is frozen and stage 11's tap must be live. Preserve cached tensors as immutable and keep the same token order, autocast context, checkpointing and precision conventions. Cache lifetime is one scene and run.

Let a column vector `z_i` be a cached patch feature of channel dimension C. The corrected suffix input is

```text
z'_i = z_i + B A u_i
A has shape [4, C]. B has shape [C, 4]. Both are shared across patches and views.
```

Use one gate/mask for all three new arms. For a patch with reliable correspondences, set `u_i = z_i` in the own-feature arm, `u_i = mean(valid donor features) - z_i` in the geometric arm, and the same difference with shuffled donors in the shuffle arm. For an unsupported patch set the correction to zero. Using the same mask gives the generic control the same support information. Charge the mask-building cost wherever it is used. All three have exactly **8C new parameters**, identical initialization, optimizer, learning rate and steps, and a unit residual multiplier. Initialize A like v1 LoRA-A using a dedicated deterministic generator and B to zero. Keep the suffix tensors and render RNG identical across arms. On the first backward pass B can have a gradient while A's is zero. Check A again after B updates.

**Build the correspondences once.** Apply no correction in the original prediction pass. Use its detached camera estimates and depth and the supplied camera priors to construct a sparse patch correspondence list. Lock the following choices before reading development scores.

1. Use the crop-adjusted camera matrix in pixel coordinates, the actual patch stride and centres, and axial depth. For zero-based patch column j and stride p the centre is `p*j + (p-1)/2`. Use bilinear sampling of depth at pixel centres. Do the entire camera calculation in FP32. Assert the grid, depth convention, padding and pixel-centre mapping on a known synthetic plane.
2. Express predicted depth in prior-camera translation units. For distinct nondegenerate camera pairs compute the ratio of prior to predicted camera-centre distances and take their median as one positive scene scale. Use all pairs whose two distances are finite and exceed 1e-6 in their respective units. Require at least two valid pairs. Multiply every original predicted depth by that scale. Log pair counts, scale and spread. If the scale is undefined, activate the plain cached fallback for that scene, charge the attempted work and score the result. No reference geometry enters this calculation.
3. For each receiving patch in view i, backproject its centre with its scaled depth and supplied intrinsics. Transform into every other view j with the **world-to-camera** relative transform `T_j inverse(T_i)`. Project with `K_j`. Require finite positive depths, an in-image match and valid target sampling support. Reject if projected depth differs from the target initial depth by over 5% of that target depth, or the reverse projection using target depth misses the original centre by over half one patch stride. Use the nearest valid target patch centre for the feature, with a deterministic tie rule. Average the accepted donor features equally. Use exactly these thresholds in the first registered experiment.
4. Construct the shuffled control independently of the render sampler. Within each ordered view pair, list the surviving receiving edges in row-major order. Cyclically permute the donor IDs by a seeded nonzero shift, preserving each receiver's support and the donor multiset. With a single edge leave it in place. Count the fraction of edges and receivers whose donor identity actually changes, including duplicate donors. Report when the control provides little separation.
5. Cache indices, masks and counts. Exploit linearity when memory is tight: project detached features to rank 4 once **per update**, gather and average in rank space, then apply B. This computes the same linear correction as averaging full-width features, up to floating-point order. A changes at each update, so never reuse stale projected values. Use the same operation order in the true and shuffled arms and compare with a dense FP32 reference on a toy scene. Preserve gradients to both factors. Include all cost in the timer. Apply the learned correction in the final readout using the correct precision-context boundary cache.

**Qualification before scoring.** Test identity cameras and known translation/scale, centre projection and round-trip, occluded and out-of-frame pixels, absent correspondences, camera inversion, invalid scale and the shuffle invariants. Check the identity of the zero-initialized candidate against cached last-12 for both heads and the final FP32 geometry. Test reordered views, fresh scene reset, and cache invalidation. Prove frozen weights and early taps stay unchanged, the suffix and boundary factors update, and final predictions actually use the boundary factors. At one step use the prior fixed-adjoint fixture to isolate implementation errors from renderer variation. Run real-loss same-seed repeats to establish the ordinary numerical envelope. Only real TCO loss may generate scientific results. Add a leakage check that replacing evaluator references with dummy values leaves prediction hashes unchanged with the same deterministic settings. Commit qualification receipts before collecting scores.

## 5. Measure and decide

Start the synchronized primary timer with CPU-loaded model and scene, before any GPU placement. Include transfers, the initial prediction, matching, cache build, every update, any fallback, final reconstruction and FP32 unprojection. Keep evaluation outside the timer. Record cold time from checkpoint load, scene time, uninterrupted peak allocated and reserved VRAM, host peak RAM, cache and correspondence bytes, and GPU/device state. Log coverage per view, valid partner counts, shuffle change rate, scale, initial/final TCO losses and parameter deltas. Keep heavy instrumentation separate from timed jobs.

Use v1's fixed reference mask and FP32 readout for every arm, then Umeyama similarity alignment, rigid ICP and bidirectional nearest-neighbour distances with the same scorer settings. Report **surface accuracy** (prediction to reference) and **completeness** (reference to prediction) in mm. Report valid point count and normal consistency as diagnostics. Keep failure and fallback counts visible. A method cannot satisfy the resource and quality claim with an unresolved OOM or missing required comparison.

For each metric take the median over three seeds within each sequence for each arm; divide candidate median by full-40 median. Average sequence ratios within physical room, then weight physical rooms equally. Speedup is the reciprocal of the resulting time ratio. For each dataset also show every room's ratios, absolute distances, spread, worst room and count above 1%. The headline estimand is an **average** across scenes. A claim about every room requires every room to pass.

| Decision | Rule |
|---|---|
| Resource and quality pass on development | Mean time ratio ≤0.50, memory ratio ≤0.80, accuracy ratio ≤1.01 and completeness ratio ≤1.01, using unrounded values. A gain in one quality metric cannot compensate for loss in the other. |
| Equal-time challenge | Among qualifying full-decoder budgets whose measured aggregate time is no greater than the candidate's, compare with the one with the smallest mean of its two full-40-normalized quality ratios (ties go to the shorter time). Include the timing-selected integer budget. Require a smaller mean normalized error and neither individual error more than 1% above this control. If even one full update is slower, compare with zero and describe that limitation. |
| Evidence for cross-view geometry | At ten steps compare the true-match arm to plain cached, own-feature and shuffled arms on identical room/seed blocks. Require a strictly smaller mean of the two normalized errors versus each, with neither individual aggregate error over 1% worse than any of them. Verify Chess completeness improves against plain cached and both Heads errors remain below full-40 medians. Show all paired effects, including Fire. Mere reduction of the training loss gives no evidence for the claim. |
| What advances | Eligible candidates are the fixed settings and the generic or geometric adapters passing resource, quality and equal-time gates. Geometry also needs its mechanism rule. Shuffled and zero are controls. Nominate the fastest eligible arm, then lower peak memory, then simpler implementation for an exact tie. Freeze one exact recipe, fallback, comparator and source hash in Git before opening confirmation results. |
| What ends the search | If no candidate qualifies on all three development rooms in aggregate, publish the measured frontier and which requirement failed. If the simple or generic arm wins, evaluate that recipe and label its contribution accordingly. If a qualified geometry candidate later ties shuffled or generic on unseen scenes, report the efficiency finding separately from the unsupported mechanism. |

Chess gives a useful scale for interpretation. The previous medians for full 40 were 17.13 mm accuracy and 21.19 mm completeness. Getting that room within 1% meant reaching about 17.30 and 21.40 mm versus 17.90 and 23.70 mm from the cached method. Use the new matched reference for decisions.
